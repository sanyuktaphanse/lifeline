# Decisions

This file records product decisions for Lifeline, newest last, with the date each one was made.

## 14 September 2026

1. China is added as the fourth corridor.
2. The China corridor is led by knowledge, pre check, trace, and Protect.
3. Lifeline moves no money in China, and it never advises any way around the quota.
4. If time runs short, India depth is the first corridor item to be cut.

## 18 September 2026

1. `Action` gains an optional `instrument_id`, and the confirmation token signs it. Task T14 freezes a lost card and task T15 sends the student to the issuer's app when the freeze is not supported. Neither can be built while a token to freeze a card does not say which card.
2. `Mandate` gains `payee_added_at`, the time each payee was added, and `cooling_hours`, the waiting time before a new payee can receive a transfer, 24 hours unless set otherwise. Task T09 adds a payee and tells the student it needs confirmation and a cooling period, which cannot be built without knowing when the payee was added and how long the wait is.
3. Rule R14 refuses a transfer to a payee added less than `cooling_hours` ago, and its reason states when the transfer becomes allowed.
4. `AgentReply` gains an optional `freeze` field holding the `FreezeResult` of a freeze that was executed. Task T15 has to send a student whose issuer does not allow the freeze to the issuer's app. The frontend needs the status and the deep link as data it can turn into a button, not only as words inside the reply text, which it cannot parse reliably in three languages.
5. `Action.amount` has a schema ceiling of one hundred million. No student transfer comes near it, so a larger figure is a mistake or an attack and is rejected before it becomes an action.
6. The agent loop remembers the last twenty messages of each student's conversation, tool results included, and gives them to the model on every call. Twenty covers several turns of tool use while keeping each request small.
7. Standing mandates use the existing `StandingMandate` model. Its `schedule` is written `monthly:D`, with D from 1 to 28 so every month has the day, due at 00:00 UTC on that day; a period is the calendar month of the due date.
8. A standing run may happen from `notice_hours` before the due time until 24 hours after it. `cancel_window_hours` may not exceed `notice_hours`, so a run can happen by the due time, and the cancel window counts from when the notice was actually written, so a student always gets the whole window to cancel.
9. `ActionType` gains `create_standing_mandate` at tier T2 with the warning key `warn.standing.new`, and `cancel_standing_run` at tier T1. `Action` gains `standing_mandate_id` and `standing_terms`, and the confirmation token signs both, so a token for one set of terms is refused for another.
10. `Source` gains `standing_mandate` for runs the agent loop starts on the student's behalf. R01 accepts it only on a transfer whose `standing_mandate_id` names an active standing mandate the student confirmed before the run.
11. Rule R12 allows a transfer within its standing mandate's pattern at tier T1 without confirmation. Rule R13 treats a transfer outside the pattern as an ordinary T2 transfer needing confirmation, and its reason names every part that fell outside. Neither rule lifts the money rules: a run still passes R03 to R09 and R14.
12. A standing mandate's id is the student's id, `standing`, the turn, and the call number, such as `student_001-standing-1-1`, so the loop and never the model chooses it. A run's receipt names the standing mandate id as its `mandate_ref`, because that is the authority the run was paid under.
13. A run's receipt keeps the mandate version id as its `mandate_ref`, like every other receipt, so `mandate_version` always resolves it. `Receipt` gains an optional `standing_mandate_id` naming the standing mandate the run was made under, and the run's execution and receipt entries carry it too. This replaces the last sentence of item 12.
14. The API checks for due standing runs once a minute while it runs, and `POST /standing/run_due` runs the same check at a chosen time for demos and tests. The endpoint is refused when `LIFELINE_ENV` is `production`, because choosing the time would let a caller bring a run forward.
15. `ActionType` gains `deactivate_standing_mandate` at tier T1: stopping payments is the safe direction, so it needs no confirmation. It marks the standing mandate inactive in a new mandate version, and rule R12 refuses any transfer under an inactive standing mandate instead of escalating it.

## 22 September 2026

1. `ConfirmationRequest` gains an optional `council` field holding a `CouncilAdvice`: the chosen rail or the word wait, the runner up, the plain reason, the disagreement score, and the triggers that convened the council. The frontend has to show what the council said beside the confirmation, and reading five facts out of a sentence in three languages is not something it can do reliably. The voices themselves are not in the field; the whole deliberation is one `council` ledger entry, which is where a record belongs.
2. The reply names the runner up only when the disagreement score is above 0.4. Below that the council is close enough to agreement that a second rail is noise, and above it the student is being told a real choice was made against a real alternative. The figure is a product choice written once as `RUNNER_UP_DISAGREEMENT` in `core/agent.py`. It is not a sourced figure and nothing about money depends on it.
3. The chair is code, not a sixth model call. Given the same five answers it always reaches the same choice, the same runner up, and the same score, which is what lets a scenario assert on them, and one deliberation costs five calls rather than six.
4. The council is optional. `AgentLoop` takes `council=None` and behaves exactly as it did before with none. Nearly every scenario and test pays 1,200 SGD against a 1,500 limit, which is above half the limit, so an always on council would change the replies and the trails of all of them; keeping it optional is what lets the tests and scenarios that existed before it prove that nothing changed.
5. The council calls the model through its own adapter, never the agent loop's, so its five calls are outside the loop's cap of eight model calls per turn by construction rather than by arithmetic. Its models come from `ANTHROPIC_COUNCIL_MODEL` and `DASHSCOPE_COUNCIL_MODEL` when those are set, as an overlay of the ordinary environment, so a cheaper or a stronger model can be chosen for the council with no new provider code.
6. The council is advice and never a veto. It cannot remove a route, change a field of the action, touch the confirmation token, or stop a payment the engine allowed. A chair that advises waiting says so in the reply, and the student still gets the confirmation the engine allowed. A council that fails leaves a note and the payment path exactly as it was.
7. What goes back to the model as part of the `propose_transfer` tool result is the five advice fields, not the whole deliberation. The model needs to answer why that route was chosen, which the advice says; the voices and their abstentions are a record for the ledger and would only make each later turn longer.
8. A language names one of the three codes Lifeline replies in, `en`, `pt` or `zh`, wherever it crosses a boundary into a prompt. `LANGUAGES` and `LanguageCode` in `contracts/schemas.py` are the one source of that, and a test pins them to the keys of the `TEXTS` table so the two cannot drift. `ChatRequest.lang` and `ConfirmRequest.lang` in `api/main.py` accept only those codes and refuse anything else with 422, and the council reads anything else as English. A language reaches a model inside a system prompt, and an attacker brief showed a caller could put a whole sentence there through this field. `Message.lang` at the contract level is still a free string. A turn in a language the loop cannot detect, such as Hindi or Spanish, is answered in English with the code `en`, because `detect_lang` only ever returns `en`, `pt` or `zh`. A caller below the API that builds a `Message` with an explicit code Lifeline cannot write in, such as `hi` or `es`, gets English text with that code echoed back, and the same code is refused with 422 over HTTP. Open item 19 records this, and `tests/test_i18n.py` pins all three paths.
9. The agent loop validates whatever a `Council` returns into `CouncilDeliberation` before it reads, writes or shows any of it, and it refuses a chosen position that is not one of the quoted routes, the word wait, or no answer. `Council` is an interface, so an implementation this repository did not write can return anything; the loop's job is to be unable to act on it. The triggers in the record are the loop's own finding, never a council's claim about them.
10. The route a council chose is part of what the student was asked to confirm, so it is restored from the `council` ledger entry when a loop is rebuilt, and not chosen again by `_choose`. An attacker brief showed the alternative: the student confirms the bank wire and, after a restart, the same token pays Wise, and a confirmation for the simulated rail becomes a real payment.
11. A voice's reason is one sentence, and `MAX_REASON` bounds it, because the reasons of the agreeing voices are read out to the student and an unbounded reason is an unbounded reply.
12. A council is offered the routes `_choose` considers first, the real ones when any are usable and the simulated ones only when none are, and the escalation rule compares the cheapest and the fastest within that same set. On the demo corridor the simulated Pix route costs nothing and arrives in an hour, so a council shown every usable route has a standing reason to choose the route that moves no money. `_considered` is that set and `_choose` is the cheapest within it, so the preference for real money is written once.
13. The API runs with a council only when `COUNCIL` is `on`, `true`, `1` or `yes`. Five model calls for every escalated transfer, and nearly every demo transfer escalates, is a cost a demo should opt into. `create_app` also takes a council directly, which is how the API tests wire scripted voices without a network.
14. An abstaining voice's raw text is kept in the record, cut at `MAX_RAW` with a marker. The transcript's job is to show what the voice actually said, and a model that answers with a wall of prose should not be able to write that wall into the ledger.

## 6 October 2026

1. The reply reads out one council sentence: the chosen rail, then the reason of the most confident voice that agreed with the chair, in the student's language. Voices equally confident are settled by the voice order cost, speed, safety, rules, timing. In the first real run on 26 September the four agreeing voices' sentences were read out one after another, a paragraph the student had to read before confirming 1,200 SGD. The full composed reason stays in the `council` field of the `ConfirmationRequest`, unchanged, for the app to show on request.
2. A wait from the safety voice always reaches the student. When the safety voice's validated position is wait, its reason is read out as one plain sentence before the confirmation prompt, whatever the disagreement score, and the confirmation is still offered, because the council advises and the student decides. In the real run the safety voice said to verify the landlord's details or send a small test amount first, on a first transfer to a new payee above half the limit, and the student never saw it because four voices outvoted it. The runner up rule at 0.4 is unchanged for every other voice, so a wait from any other voice alone is not read out below the threshold. When the chair itself chose wait and the safety voice is its most confident voice, the chair's sentence carries no reason, so the same sentence is not said twice.
3. The voice contract tells every voice to use only facts present in the context, and when the context holds no due date, deadline or late fee, not to mention one. In the real run two voices wrote about a due date and a late charge that the context did not carry.
4. Every status error either provider's SDK raises becomes a `ModelAdapterError` carrying the provider, the status code and the provider's own message, never the key, and the API answers it with a 503 naming the provider and the reason. The fallback policy is unchanged: only a connection failure, a missing key, 401 and 403 switch providers.
5. `DASHSCOPE_BASE_URL` sets the HTTP base URL of DashScope calls when it is set, and changes nothing when it is empty. A Model Studio key works only against its own region's endpoint, so the endpoint is configuration with its source cited in the technical reference, never a URL written into the code.
6. The runner up follows the same rule as the chosen rail: one sentence, the reason of the most confident voice that took that position. The threshold of 0.4 for naming it is unchanged.
7. No voice brief gives an example of a fact. The speed brief said "such as a rent paid after its due date", and in the first real run the speed voice wrote about a late rent charge the context did not carry. A brief names what a voice weighs, never a fact it might find.
8. A guard in `tests/conftest.py` fails any test that reaches `anthropic.Anthropic` or `dashscope.Generation.call`, for the whole suite, whatever `.env` holds. A guard in one test file protected only that file, and API tests reached Anthropic for real on a machine whose `.env` turned the council on.

## 8 October 2026

1. The emergency top up of rescue step S5 is an ordinary T2 transfer through `propose_transfer`, with the usual confirmation and every usual rule. It is not a standing run, because R12 only runs monthly schedules. The plan's `emergency_allowance` is the amount the rescue proposes, never an authority to pay.
2. A rescue step that would need a fact with no knowledge entry behind it says Lifeline has no sourced figure and points the student at the issuer's app. It never guesses, which is CLAUDE.md rule 4.
3. `ActionType` gains four types: `rescue_identity_check` at T1, `check_wallet_token` at T0, `reroute_to_backup` at T1, and `notify_family` at T1. The brief named three; the wallet token check of step S3 needed a T0 type of its own, because none of the existing T0 types reads a plan. The engine refuses `reroute_to_backup` without an instrument under R04, as it refuses a freeze without one. `tests/test_interfaces.py` now pins every action type with its tier.
4. `contracts/schemas.py` gains `Plan`, with `PlanCard`, `TrustedContact` and `IdentityCheck`. A trusted contact holds a name and a channel and refuses any other field, so a phone number or an email cannot be stored. The expected identity answer is a `SecretStr`, so it never prints and never dumps. The plan names its cards by the name the student gave them; the primary and the backup must be among them and must differ.
5. The plan gains four fields beyond the brief's list: `cards`, so a student whose plan names no primary card can choose one by its plan name; `replacement_estimates`, mapping an issuer to the knowledge entry holding its card delivery estimate, in the shape of `cash_plan`; and `emergency_payee`, `emergency_corridor` and `emergency_purpose`, so step S5 knows where the allowance goes. The engine still checks that payee under R06 and R14 like any other.
6. The demo and harness mandates gain the payee `self_sg`, the student's own Singapore account, the corridor `SG>SG`, and the purpose `emergency`. `self_sg` was added on 1 January 2026, so it is never inside its cooling period, and the 300 SGD fixture allowance is inside the per transaction and daily limits, so the demo is never refused for a reason that is not the point. The fake router quotes one fixture Wise route on `SG>SG`.
7. The rescue never calls the model. The code builds every call a rescue makes: the freeze of the plan's card, the allowance transfer, and the stops of the standing payments. The model handles only free text, through `/chat`, during a rescue as at any other time.
8. Rescue messages never join the conversation memory, so the identity answer never reaches a model. Each rescue call still writes a `turn` entry.
9. A trigger that arrives as pasted text or a tool result is written as a note of kind `rescue_trigger_ignored` with its source, never as `rescue_started`, so a rebuild can never read it as a start. A rescue step whose message is data asks the engine for the waiting step's action with that source, and the engine refuses it under R01.
10. Step S5 proposes the allowance as soon as the machine reaches it; the student asks for the money by confirming it, and a step with no token continues without it. A skipped allowance's confirmation is closed, before and after a restart, so it cannot be confirmed later.
11. A refusal or a `not_supported` or `failed` freeze does not stop the machine. The student has been told the truth, and the family notice reports it.
12. `StandingMandate` names no card, so step S8 stops every active standing mandate with `deactivate_standing_mandate` and says so. Stopping is permanent, so the reply says the student has to set them up again once the new card works.
13. `reroute_to_backup` records the frozen card, the backup card and the backup route in its execution entry, and the loop reports the live card. No payment reads a card, so nothing else changes; open item 70 records it.
14. Every transition of the machine is a note of kind `rescue_transition` naming the event, so a new loop replays a rescue through the same transitions it took.
15. The family notice is built only from this rescue's ledger entries, in the student's language, so it reports every refusal, every rejected confirmation, every blocked injection, every wrong identity answer, and a freeze that was not supported. It is written as a note of kind `family_notice` addressed to the trusted contact. Nothing is sent; the app delivers it.
16. Knowledge entries checked by Claude Code against the page it opened carry `CC` in `checked_by` and an empty `second_check_by`, until a person checks them and replaces `CC` with their initials.
17. A token that confirms a rescue step is confirmed only through the rescue. `/confirm` refuses it with `confirmation_rejected` and the reason `rescue_step`, and leaves it waiting. An attacker brief showed that confirming the allowance through `/confirm` left the machine at S5, so a later step reported the paid allowance as skipped.
18. In the rescue, a token used before, closed, or never issued changes nothing, and a step is offered again only when nothing of it is waiting. An attacker brief showed a double tap on the freeze ending the money step, and a forged token stacking a second allowance that could be paid after the first.
19. A restart that falls between two steps needing nothing from the student runs on from there at the next call, rather than resting where the machine never rests.
20. The engine refuses under R04 a new payee id that is not plain ASCII letters, digits, the dot, the at sign, the hyphen, and the underscore, and a card id given to a freeze, a reroute, or a wallet check that is not written `issuer:card`. The provenance check compares a payee id with compatibility forms folded, invisible characters and outer spaces removed, and case ignored. An attacker brief showed a pasted payee padded with a space or a zero width character trusted as the student's own, a lookalike letter offered for confirmation, and pasted prose frozen as a card id and copied into the family notice.
21. The family notice tells a transfer as sent only when its receipt completed, as failed when the receipt failed or was returned, and as started with its status otherwise; and as a simulation when either the route or the receipt was one.
22. A `422` from a rescue endpoint drops the request body from its detail, and the plan hides its input from validation errors, so neither can carry the identity answer. Other endpoints keep FastAPI's default, which open item 79 records.
23. A rescue locks at S1 after three wrong identity answers. Three is a product choice, not a sourced figure: it lets a student mistype twice and still go on, and it stops a stranger from guessing a four character answer through an API with no sign in. It is `MAX_IDENTITY_ATTEMPTS` in `core/agent.py`. A locked rescue compares no further answer and proposes no action for it, writing only a `rescue_locked_attempt` note, so the loop never refuses on its own and the engine is never asked about an answer that will not be compared. The lock is written as a note and counted again on restart, so it survives one, and the family notice is written at the moment of the lock, because a locked rescue never reaches S9. Nothing unlocks it yet.
24. A transfer reply, inside a rescue or outside one, says what its receipt's status says: that the money was sent only when the receipt is completed, that the transfer failed and no money arrived when it failed or was returned, and that it is not completed, naming the status, for any other. It is the rule the family notice follows since the second attacker brief, applied to what the student hears.
25. Every Python excerpt in `docs/code-walkthrough.md` is checked against the file it names by `tests/test_walkthrough.py`, so the walkthrough cannot drift from the code again without a failing test. The check found 21 excerpts that had drifted, most of them by this stage's own changes, and they were copied again from the source.
26. SP checked `sg_cash_pickup_001` and `sg_card_replacement_002` against their pages, so `checked_by` holds SP in place of CC. `second_check_by` stays empty until a second person checks them.
27. `Route` gains two optional fields, `purpose` and `payee_id`, both None by default, so every route made before them is unchanged. A simulated rail has to see what it carries: UPI to PayNow allows only the purposes its entry names, Pix reaches a payee only through a Pix key, and the China rail pays a student's own account but never an institution directly. `Rail.execute` receives only a route, so the route must carry them. The router names the purpose it quoted for. The loop stamps the payee on the route it is about to pay, in `_pay_on_route` and nowhere else, so the route the student was offered and the token they confirmed are untouched, and the execution entry records the stamped route the rail actually received. `tests/test_interfaces.py` pins the new shape.
28. `TraceResult.typical_duration_hours` is optional, None by default. A trace on a rail whose entries give no duration, such as a remittance from China to a student's account in Singapore, has no figure to give, and a zero would read as no time at all. When it is None, `typical_duration_source` names the entry and says Lifeline has no sourced duration on file. `tests/test_interfaces.py` pins it.
29. A knowledge entry may carry `values`, the figures and lists of its statement as data, such as the UPI to PayNow daily cap of 60,000 rupees and its two permitted purposes. The router and the simulated rails read a limit, a purpose, or a document list only from there, by entry id, and never write one themselves. `tests/test_knowledge_values.py` checks that every number in `values` is written in the entry's statement. A duration of zero hours is allowed only where the statement says real time.
30. Money sent to the student, such as a parent's transfer that has not arrived, is seeded into its rail on every start from the fixture's `inbound_receipts`, through the rail's `restore`. The student did not send it, so nothing about it is written to the ledger. The loop is given, per student, which rail holds each such receipt, so the trace tool finds it exactly as it finds a receipt the student's own payment produced. This closes open item 52.
31. The router quotes UPI to PayNow, now named `upi_paynow_sim`, only for the purposes `in_upi_paynow_purpose_001` names, `maintenance_of_relatives_abroad` and `gift`, exactly as the RBI states them, and blocks any other purpose with a reason listing the permitted ones and the entry id. It blocks an amount above the daily cap of `in_upi_paynow_cap_002` with that entry's id. The earlier fixture purposes, allowance and family support, were not what the source says and are gone. Each simulated route carries the entry it rests on as its `rule_id`, which is what a council voice may cite. `fee_source_url` stays null, because the entries source rules, not fees, and the fees and arrival times stay fixtures marked as such.
32. The router quotes China to Singapore over `cn_bank_remit_sim`, always blocked. Paying the institution is blocked because NUS asks for payment through Flywire or Convera and no sourced rule is on file for a direct bank remittance to it, citing `sg_nus_fee_payment_003` and `cn_edu_remit_002`, which describes HSBC's service for schools in other countries. Funding the student, through Bank of China's An Xin account in `cn_boc_anxin_009`, is blocked because no entry gives a duration. Any other purpose has no sourced rule. `Route.arrival_hours` needs a number, so a blocked China route carries zero as a fixture, and its reason says why. The precheck `remit_from_china` gives the Bank of China checklist, the Chinese side's quota and identity rules from `cn_fx_quota_001` and `cn_cdd_004`, and that no sourced duration is on file, and nothing else.
33. Every simulated rail runs one of five scripts, `normal`, `delayed`, `held_for_review`, `returned` and `scam_text`, chosen when the rail is built: the harness reads `fixtures.rail_scripts`, a rail name to a script, and the API always runs `normal`. A script is never chosen by idempotency key, because the loop makes the keys and no scenario can choose them.
34. `ReceiptStatus` is unchanged. Each provider stage maps onto an existing status, the China rail's documents submitted, under review, released, in transit and arrived onto created, held for review, funded, in transit and completed, and the provider's own wording goes in the trace's first next step. The simulated time between stages, one hour for UPI to PayNow and 48 hours for the China rail, is a fixture marked as such, and so is the scam text.
35. The Pix rail completes a normal transfer at execute, because `br_pix_instant_001` says the funds reach the payee in real time. Its delayed script issues it as created and stops there, so a reply says it is not completed. T29's receipt is still `sim_pix-0001` and its reply still says the money was sent.
36. The Pix rail keeps the name `sim_pix` and the corridor SG>BR, and replaces the plain fake of that name in the harness and the API. It pays only a payee whose id is in `pix_key_on_file`, a fixture that names payees and never holds a key, with `landlord_sp` in it so every existing scenario passes.
37. Lifeline never proposes a transfer from China to Singapore. Decision 3 of 14 September says Lifeline moves no money in China; no mandate allows the corridor, and a test proves the engine refuses such a transfer under R05. The China rail's `execute` exists for the `Rail` interface, requires the Bank of China checklist and a known quota position, and is exercised only by its own tests. The rail carries parents' transfers seeded as inbound receipts, which the student can trace.
38. The ten to fifteen business days in the Stage 7 brief were withdrawn, because no entry gives them. The entry governs: the China rail's trace carries no duration and says so.
39. `sg_nus_fee_payment_003` was written from sentences SP read on the NUS page in a browser, because the site's bot protection blocked the tool twice. Its `checked_by` is SP and its note says why. Its statement holds only those sentences.
40. T36 is answered by the precheck `remit_from_china` and two quotes, and `PrecheckResult` was not widened. The model is given, from entries only, the Bank of China checklist and that no duration is on file for funding the student, NUS's sentences for paying the institution, and the Chinese side's quota and identity rules. When to start is said only in the entries' own terms, never as a date.
41. T18 stays not automated. UPI to PayNow is the parent's remittance from India under the Liberalised Remittance Scheme, and the student's mandate is in SGD, so the student cannot make it; it needs the parent as a user with a rupee mandate. T19 and X15 are automated as quotes in rupees.
42. `SIM_RAILS` turns the API's two new simulated rails off when it is `off`, `false`, `0` or `no`, and leaves them on otherwise, empty included, so the demo has them by default. It is in `.env.example`. The tests pass `sim_rails` to `create_app` explicitly.
43. X14's expectation changed with the rule it checks: the router's blocked reason now comes from `in_upi_paynow_purpose_001` and names the RBI's purposes, so the scenario expects that sentence instead of the old fixture's.
44. The UPI to PayNow cap is the sender's day in India. The RBI entry says "in a day" for remittances from India, so the rail takes the day in the Asia/Kolkata zone from the time zone database rather than a UTC day, which would let 120,000 rupees through across a UTC midnight. A sender is the mandate reference without its version suffix, so a new mandate version does not give a parent a second cap the same day. The day's total is compared with the cap as exact fractions, so no decimal precision rounds a sum back under it. All three came from the number audit of 8 October.
45. The `sim_pix` route's arrival time is read from `br_pix_instant_001`, the entry it cites, so it is zero, real time, where it was a fixture of one hour that contradicted that entry. T17's expectation changed with it.
46. `tests/test_knowledge_values.py` checks every number in an entry's `values`, floats and numbers inside lists and mappings included, against the statement as a whole number, so a cap of 60 is not found inside 60,000.
47. The provenance check reads the student's words and the data with one rule: compatibility forms folded, such as fullwidth letters, and invisible characters removed, the way a proposed payee id was already read. An amount is read both as written and with a thousands grouping of a space, a no break space, a narrow no break space or an apostrophe closed up, so 1 400 and 1'400 are 1400. The scam text attacker brief showed a scam account hidden by a zero width space, a soft hyphen or fullwidth letters, and a fee grouped with a space, each reaching a confirmation instead of a refusal under R01.
48. A payee id or an amount that only the model has named, in its own earlier replies, counts as data and is labelled as tool output, because the model's words come from what it was given. The same brief showed a model warning "do not pay" an account in every reply, so the account stayed in view after the tool result that named it had left the twenty message memory, and a later proposal to add it was offered for confirmation. A detail the student typed is trusted as before, so this changes nothing for a payee the student named.
49. SP checked `in_upi_paynow_purpose_001`, `in_upi_paynow_cap_002`, `br_pix_instant_001`, `br_pix_keys_002` and `cn_boc_anxin_009` against the RBI FAQ, Resolution BCB 1 and the Bank of China An Xin page in a browser on 8 October 2026, so `checked_by` holds SP in place of CC. `second_check_by` stays empty until a second person checks them.
50. Lifeline anchors its ledger head. The hash chain is checked by Lifeline's own code against its own file, so a forger who rewrites every entry from an edited one onward leaves a chain that verifies. An anchor writes the head hash and its sequence number outside the ledger, signed, so a copy of the ledger can be compared with it. Nothing about money goes into an anchor: only the head hash, its sequence number, a SHA 256 of the user id, and a time. The local signed anchor, a line in `data/anchors.jsonl` with an HMAC under `LIFELINE_ANCHOR_SECRET`, is the first half of Stage 5; FISCO BCOS is the second, and until it lands `ANCHOR=fisco` stops the API with a not configured error rather than falling back.
51. The loop anchors after every execution whose action type is T2 in `core/tiers.py`, and at least once in each hour of activity, measured on the loop's clock from the last anchor, or from the first ledger entry when there has been none. The hour is a product choice, not a sourced figure; it is `ANCHOR_INTERVAL` in `core/agent.py`. The static tier is used, so a standing run, which the engine decides at T1, still anchors, because it moves money. An hour with nothing written anchors nothing again.
